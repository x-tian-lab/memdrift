# CLI 界面初稿：从「敲命令」到「看得见、点得动」

状态：**初稿，待选方向**。三个方向都只是效果图，选定后再写代码。

## 问题

现在的 CLI 是十二个并列的子命令。会用的人觉得干净，没用过的人第一反应是：

- 不知道该敲哪个（`diff` 和 `show` 有什么区别？`revert` 要带几个参数？）
- 输出是一列文字，看不出「哪一处该紧张」
- 撤销要先查字段名、再拼参数，错了只能重来

终端本身不是问题，问题是它只提供了一种交互方式：**你先知道要什么，它才给你**。

## 三个方向

### 方向一 · 全屏 TUI 仪表盘（`memdrift ui`）

一个常驻界面：左边是提交时间线，右边是选中的那次提交的字段级变化。

- `↑` `↓` 选提交，`enter` 展开某处变化，`r` 撤销，`/` 筛选页面，`q` 退出
- 低置信度、整值替换的条目直接标「建议复核」，不用自己读 `change_ratio`
- 撤销前先出计划（就是现在的 `--dry-run`），按 `y` 才真写

适合：每天要看、习惯键盘、可能在 SSH 里的人。
代价：引入一个 TUI 库（`textual`），README 里「三个依赖」的说法要改。

### 方向二 · 向导式入口（直接敲 `memdrift`）

不带参数时不再打印帮助，而是开始一段问答：先告诉你「昨晚改了 6 处，1 处建议看」，然后一处一处过，像处理邮件。

- 每屏只问一个问题，每一步都告诉你会发生什么
- 「撤销」永远是一个新增 commit，确认前把这句话摆在屏幕上
- 老用户不受影响：子命令原样保留

适合：第一次用、不想读文档的人。它和 `docs/onboarding.html` 是同一条路径的终端版。
代价：流程要设计得足够短，否则会变成「按回车模拟器」。

### 方案三 · 可操作的本地网页（升级 `serve`）

`serve` 现在是只读的。加上时间线、字段级 before/after、证据，以及一个「撤销这一处」按钮（点两次：先出计划，再确认）。

- 零新依赖，复用现有的事件流和脱敏层
- 一条命令 `memdrift ui --open` 直接开浏览器
- 写操作走已有的 token + Host/Origin 校验

适合：不想留在终端里的人，或者想投屏给别人看。
代价：网页里的写操作要多想一层安全；移动端不适合。

## 怎么选

| | 方向一 TUI | 方向二 向导 | 方案三 网页 |
|---|---|---|---|
| 新依赖 | 1 个（textual） | 0–1 个 | 0 |
| 上手成本 | 低（有按键提示） | 最低 | 低 |
| 熟练后的效率 | 高 | 低 | 中 |
| 能在 SSH / 无桌面环境用 | 能 | 能 | 不能 |
| 支持写操作（撤销） | 是 | 是 | 是 |
| 工作量 | 中 | 小 | 中 |

三个方向共用同一层内核，和现在的 CLI 一样：`events.build()` 出事件流，`revert.plan()` 出计划，`revert.execute()` 落盘。换界面不换规则，脱敏和「先看计划再写」在任何界面里都成立。

我的建议：**先做二作为默认入口，再做一**。理由是它们可以共用同一个「时间线 + 选中 + 确认撤销」的内核，向导是它的线性版，仪表盘是它的自由版；三可以之后再做，因为它是最便宜也最不着急的。

## 不管选哪个都要成立的几条

1. **撤销永远是先计划、后确认、再写。** 没有任何界面提供「直接改」。
2. **风险标记只有两类**：删除、大面积改写。低置信度只在提交级别提示一次，不把每一行都染红（W2 时试过，结果是满屏红字，等于没有标记）。
3. **终端里不出现绝对路径。** 和 digest、MCP 用同一个脱敏层。
4. **`--json` 和现有子命令不动。** 脚本和 MCP 工具不受影响。

## 选定之后要定的细节

- 向导每屏显示几处？超过多少条时改成「只列需复核的」？

- 网页版的写操作要不要额外要求一个本次会话内有效的确认码？
